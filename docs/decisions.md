One entry per decision: date, what, why. Newest entries go at the bottom.

- 2026-11-04 (superseded by the entry on the two Vitest projects below): Vitest is scaffolded with `usages:unit`, so there is no browser or jsdom project and no Testing Library yet. Why: week 1 tests run in node only; jsdom and Testing Library are added with the first component test, so nothing is installed before it is used.
- 2026-11-04: `package-lock.json` is generated with npm 11 (`npx npm@11 install`). Why: npm 10.9.8, bundled with Node 22, crashes on a fresh resolve with `Cannot read properties of null (reading 'edgesOut')`. `npm ci` works with npm 10.9.8 on this lock, so CI is unchanged. Use npm 11 for dependency changes.
- 2026-11-04: We use `#lib/*` subpath imports (`imports` in package.json) for `src/lib`, not `$lib`. Plan mentions of `$lib/...` mean `#lib/...`. Why: SvelteKit 3 removed the `$lib` alias, and the `alias` option that brought it back is deprecated (`config_option_deprecated_alias` on every build).
- 2026-11-04: ESLint ignores `docs/` and `showcases/`, the same scope as `.prettierignore`. Why: `docs/questions/server.mjs` (kickoff material) fails `preserve-caught-error`, and course material and generated showcases do not follow our lint rules.
- 2026-11-04: Class diagram member types turn `{`, `}` and `=>` into Mermaid entity codes (`#123;`, `#125;`, `#8594;`) and every `"` into `#quot;`; sequence messages ignore the optional `label` field. Why: Mermaid parsed `{ a: string }` and `"open" | "done"` as the end of the class body or a syntax error (checked with mermaid-cli); the sequence syntax in the plan shows only `method(params)`.
- 2026-11-04: Project names match `/^[a-z0-9][a-z0-9-]{0,40}(@P[1-7])?$/` instead of the plan's `/^[a-z0-9][a-z0-9@-]{0,40}$/`. Why: the plan's regex rejects the checkpoint names `todo@P2` (uppercase `P`) that spec section 12 and the Task 6 test require; names stay lowercase so `Todo` and `todo` cannot collide on a case insensitive file system.
- 2026-11-04: Run backups live in `.aise/runs/<id>/backup/<rel>` next to `backup/created.json`, so a project file named `created.json` at the project root cannot be written inside a run (it throws `PathError`). `PathError` lives in `core/path-error.ts` and `store.ts` re-exports it. `ProjectStore` also has `readText`, `writeJson` (validates with zod, two space JSON with a trailing newline) and `appendFile` (chat and run event logs, not backed up). Why: keeps the backup layout from the plan unambiguous, avoids a runtime import cycle between `store.ts` and `runs.ts`, and gives every JSON write one validated path.
- 2026-11-04: `callModel` returns a narrowed `ModelResponse` (content, stop reason, stop details, usage) instead of the SDK `Message`, and all three models go through `client.beta.messages.create`; Haiku just omits the `betas` and `fallbacks` parameters. Why: the beta message type differs from the stable one (for example the `advisor` server tool name), so one beta typed path keeps the loop free of casts, and the response content is pushed back into the history unchanged, which preserved thinking and fallback blocks require.
- 2026-11-04: A tool that throws unexpectedly (for example `PathError`) fails the run with its message, like an exception from the model call; usage summed so far is kept. Why: it is a bug or an I/O failure, not something the model can fix by retrying.
- 2026-11-04: Prices checked against the claude-api skill: Opus 5.5 $4 / $20 (cache read $0.20), Sonnet 5.5 $2 / $10 (cache read $0.20), Haiku 5.5 $0.10 / $0.50, cache reads 0.1x input and 5 minute cache writes 1.25x input, so the plan's `PRICES` stay unchanged. Not modelled: Haiku 5.5 costs $0.50 / $2.50 for prompts above 100K tokens (gate summaries are far below that), and a request served by a refusal fallback model is billed at that model's rates while we price it at the requested model. Why: cost is a display figure, and per request model data would complicate `Usage` for a rare case.
- 2026-11-04: `effort` is sent in `output_config.effort` for all three models (Haiku 5.5 accepts `low` to `max`, default `medium`; Opus 5.5 default is `medium`, Sonnet 5.5 `high`), and `fallbacks: 'default'` uses beta `server-side-fallback-2026-07-01` for Opus and Sonnet only. Haiku 5.5 has no server side fallback. Why: checked against the skill and `@anthropic-ai/sdk` 1.4.0 types (`BetaFallbacksParam`, `BetaOutputConfig`, `BetaRefusalStopDetails`); effort is always explicit because the defaults differ per model.
- 2026-11-04: Agent system prompts are static plain English with no dates or per run data, and `summariseRun` sends Haiku (effort `low`, `maxTokens` 1000, no tools) only the phase, the final reply and tool names with ok or error. It throws when the reply has no text (for example a refusal). `loop.ts` now exports `textOf` and `usageOf` for it. `tsx` is a dev dependency for `scripts/smoke-p1.ts`, which is not type checked by `npm run check` (tsconfig covers `src`) but is linted. Why: static prompts keep prompt caching working; the gate summary needs no tool inputs; the smoke script is a manual live check, not part of CI.
- 2026-11-04: Orchestrator rules beyond the plan. Every mutating action (send, approve, still valid, update, edit requirements, discard, create) claims the project synchronously before its first await; a second one gets `ConflictError` ("A run is already active" once a run owns the project, "Another action is running" before that). `Orchestrator.ready` is a promise started in the constructor that marks runs left `running` as failed (`server restarted`); every public method awaits it, so the constructor keeps the plan's signature. Sending a P2 message, `stillValid` and `updateStale` require an approved P1, like approving P2. `approve` needs something to approve (`awaiting_approval` or `stale`). `stillValid` records a failing P2 gate as an override instead of refusing. Agent history is the phase chat as text messages, consecutive same role entries merged, tool calls not replayed; a failed run with no text adds no assistant entry. `discardLastRun` takes the latest run that is not yet discarded, so repeated calls walk back. A run's cost includes its gate summary; a failed summary leaves `summary` unset and keeps the run status. `NotFoundError` is thrown for an unknown project. Why: the plan leaves these open; each choice keeps one run per project, keeps the design derived from approved requirements, and keeps phase status explainable from artefacts and `state.json`.
- 2026-11-04: The orchestrator singleton (`globalThis.__aiseOrchestrator`) and the event bus listeners (`globalThis.__aiseListeners`) live on `globalThis`, not in module scope. Why: Vite dev re-evaluates server modules on edit; a second orchestrator would have an empty claims map, mark the live run of the first as `server restarted` and accept a second run on the same project, and a fresh listener map would cut SSE subscribers off from the surviving orchestrator's events.
- 2026-11-04: Font stacks start with the family names fontsource registers (`'Geist Variable'`, `'Geist Mono Variable'`) before `'Geist'` and `'Geist Mono'`; the display font Instrument Serif ships weight 400 only, so display headings use weight 400. Why: the brief names the families `Geist` and `Geist Mono`, but `@fontsource-variable/*` declares them as `... Variable`, so the plain names would never load the self hosted files, and a bold weight on Instrument Serif would be synthesised.

Why: the scale pairs each size with a weight, and components need the 12 column count and the minimum hit area as named values rather than literals.

Why: rem values would otherwise bypass the spacing rule, and scanning the whole file would flag anchors and TypeScript.

- 2026-11-20: `deploy_check` checks compose.yaml in two steps and runs what it checked. - 2026-11-26: Fix loop (test agent and code agent work together). What: one P5 run (`fixLoop: true`, `testgen/fix-loop.ts`, approach A) owns all rounds and alternates triage, a code fix and the P4 and P5 checks, switching `ToolContext.agent` per step; it starts from the Fix automatically button and by itself after a generation run that ends `done` with an open code bug finding, on the same claim. Why: one claim means no window for another action between steps, one cost guard ($3, hard per step: each agent step gets what is left of the limit as its own guard, no step starts with less than $0.10 left, and the loop stops when a step hits its limit or the total reaches $3) bounds the spend and one Discard last run undoes the whole loop (after generation it keeps the tests). Rejected: chained runs, one per step (the claim is released between steps, Discard undoes one step only, stop rules spread over `settle`) and an `ask_code_agent` tool on the test agent (nests scopes, hard to bound and to mock). Stop rules: green; nothing left to do; a round that changed no file under `src/` or `test/`; 3 rounds; cost guard; an agent error, a timed out check or Docker down (`failed`); a triage step that changes a test file an earlier triage of the loop already changed (`done`, the developer decides). No silent weakening: attempts count per file and test name (2 at most) because a new report gets a new finding ID; triage gets the list of files it must not change again and the guard reads the files, not the prompt; the code agent cannot write `test/` and answers `test_looks_wrong` through `report_fix_result`, which sends the test back to triage once instead of changing it; `needs_design_change` is never handed back; problems are judged against baselines taken at the start, the stored P4 and P5 checks only when their hashes match the current files, else the checks run once without an LLM (a timeout there ends the loop `failed`); new typecheck errors outside `test/` and new drift are handed to the code agent and end the loop `failed` when they stay; a test file that stops loading or gains typecheck errors under `test/` ends the loop at once, `failed`, with a message naming the files, because the code agent cannot change `test/`. `report_fix_result` is in the code agent's tool list for fix loop runs only. Cost: approving P4 can spend $2 (tests) plus $3 (loop) without another click, stated in the README and CHANGELOG. Handoffs are `agent_message` events, also appended to the P5 chat with `from` and `to`. Handback after a corrected dispute: when triage corrects a test the code agent disputed and does not report the bug again, a test that still fails goes back to the code agent (within the 2 attempts), with "The test agent corrected the test; fix the code for the corrected test." instead of the retry line. Why: the dispute is settled, so the remaining failure is a code bug against the corrected test, and the code agent refused rather than failed last time. The file of a disputed test is exempt from the "do not change again" list and the changed twice guard in that triage step, else the brief contradicts itself and every dispute in an already triaged file goes to the developer. Unreported triage changes are judged per step (fixes not present before the step), so a second change to a file reported earlier is recorded too. Handoffs carry a per run `seq` so the chat dedupes live and stored handoffs by position, not by text (a retry repeats the text).
