# Browser client maps to public/ (#15)

Status: draft for approval. Source: `docs/reflection/showcase-scaling.md`, finding 6. Builds on #12 (`client` node kind).

## Goal

The browser is one component on a `client` node, with no classes. Code generation writes nothing
to `src/` for it; the page is `public/index.html`, and the trace links the component and its use
cases there. No dead TypeScript for the browser, no trace into dead code.

## Non-goals

- Bundling browser TypeScript into `public/` (esbuild): rejected as more moving parts.
- Several entry points per server node (#14).
- Splitting `public/` into several files: the page stays one `index.html`.

## Rules

- Validation issue: a component on a `client` node lists no classes (`components[i].classIds:
  a component on client node X holds no classes; the browser page is public/index.html`).
- Sequences: the browser's part in a use case is the actor's message to the first server class,
  as today for single node designs. A message sent by a class must come from a class (unchanged).
- Design prompt: the browser is one component on the client node, without classes; its reqIds
  name the requirements the page serves. UI behaviour lives in the use cases and requirements.

## Code generation

- `planCode` plans no file for a class on a client node. Since validation forbids such classes,
  this only matters for a design saved before; a regenerated project loses them through the
  update mode as removed classes.
- Wiring brief: names the client component (name, DSN ID, reqIds) and tells the agent to put
  `<!-- @trace DSN-xxx REQ-... -->` as the first line in `<head>` of `public/index.html`.
- Update mode: a removed client class deletes its file, as any removed class; a changed client
  component (reqIds) updates the `@trace` comment.

## Trace

- `core/trace.ts`: a component on a client node gets the code location `public/index.html` (line
  of the `@trace` comment, else 1) when the file exists. The use cases and requirements it carries
  reach it through the existing hops (REQ to component, use case to its REQs to component).
- Drift: unchanged. It compares `src/` with the classes; a client component has none.

## Migration

Script (scratch, not committed) over `showcases/booking` and `showcases/auction` `design.json`:
remove the classes of the client component (booking DSN-014, DSN-015; auction DSN-036 to DSN-041)
and empty its `classIds`; in sequences, a message sent by a removed class is sent by the use
case's first actor, and a message to a removed class is dropped. Validate (0 issues, 0 warnings),
regenerate `docs/design.md`. Then run P4 Update on both projects (paid, about $0.2 each) so the
client files leave `src/` and `public/index.html` gets its `@trace` line; commit the result.

## Edge cases

- Client node without a component: allowed (the page is still generated by the wiring).
- Two components on one client node: allowed, each listed in the `@trace` comment.
- A requirement linked only from the client component still counts as linked for the P2 gate.

## Tests

- Validation: client component with a class is an issue; without classes passes.
- Plan: a class on a client node gets no file (old design).
- Wiring brief: names the client component and the `@trace` comment.
- Trace: client component and its REQ resolve to `public/index.html` at the comment line; no
  location when the file is missing.
- Committed designs test stays green (0 issues, 0 warnings).

## Acceptance

- Booking and auction after P4 Update: no file under `src/` for a client class; typecheck and
  drift clean.
- The trace view for a UI use case (booking UC for listing bookings, auction place bid) shows
  `public/index.html`.
- Full gate green.
