# P7 Ticket Based Maintenance Implementation Plan

> **For agentic workers:** implement task by task; steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every maintenance change goes through a ticket (change, requirement, bug, drift): an Opus maintenance agent triages it into a plan, the developer approves, the change walks through the existing phases with their gates, and closing the ticket stores a change report.

**Architecture:** Tickets live in `.aise/tickets.json` with a chat file per ticket. Triage and the report are P7 runs of the maintenance agent, which writes only through two ticket tools. Approving a plan starts a normal chat run in the entry phase; the existing staleness cascade does the propagation. Every run started while a ticket is in progress records `ticketId` and the ticket state before it (`prevTicket`), so Discard walks tickets back like phases. The walk is the list of chat phases from the entry phase on, read from state, so P6 joins once it is in `ChatPhase`.

**Spec:** `docs/superpowers/specs/2026-11-22-p7-tickets-design.md` (read it first). Code to mirror: `orchestrator/p5.ts` (pure helpers next to the orchestrator), `core/tools/findings.ts` (run bound tools), `agents/test.ts` (agent and briefs), `components/TestsPanel.svelte`.

## Global Constraints

- Server code under `src/lib/server` uses relative imports and `process.env` only; no `$lib`, `#lib`, `$env`. UI imports `src/lib` with `#lib/*`.
- Maintenance agent: `claude-opus-5-5`, effort `medium` (house rule: never `high`). Turn limit 20. It never writes project files; its only writes are `write_ticket_plan` and `write_ticket_report`.
- `.aise/tickets.json` is never backed up by runs: ticket changes on discard come from `RunMeta.prevTicket`, so a discard never clobbers tickets created later.
- Phases are generic: the walk is `CHAT_PHASES` from the entry phase on, minus phases that are `not_started`. No code lists `P1`, `P2`, `P4`, `P5` for the walk; P6 joins when the P6 branch adds it to `ChatPhase`. Do not implement P6.
- One ticket `in_progress` per project; one run per project stays the rule (existing claims).
- No `TCK` tags in code or diagrams.
- No hyphens or dashes as punctuation in UI copy.
- Verification gate before every commit: `npm run check && npm run lint && npm test`. The last task also `npm run test:docker`.
- Decision entries in `docs/decisions.md` (date 2026-11-22, what, why) in the task that makes the decision; Task 14 collects any missing.

## Deviations from the spec (decided while planning)

1. `Ticket.runIds` is not stored: runs carry `ticketId`, and the ticket view derives its runs from `listRuns`. One source of truth; nothing to keep in sync on discard.
2. Discard rollbacks are generic: every ticket run stores `prevTicket` (`status`, `plan`, `report`) and discard restores it. This gives the spec's two cases (entry run back to `triaged`, triage run back to `open` without plan) and also covers a second triage round and the report run.
3. Close: the report data (steps, changed IDs, file diffs, test result) is built by plain code; the maintenance agent writes only the prose `text` through `write_ticket_report`, which also sets `done`. Diffs are per file over the whole ticket (earliest backup of the ticket's runs against the current file), because backups hold the before state only; each step lists the files its run touched.
4. P7 rail status is derived in `snapshot`, not stored: `running` while a ticket run is active, `awaiting_approval` while any ticket is `open`, `triaged` or `in_progress`, `approved` when all are `done` or `rejected`, `not_started` without tickets. The spec does not say what an `in_progress` ticket shows; it needs the developer, so `awaiting_approval`.
5. "Still valid" starts no run, so it cannot carry `ticketId`; while a ticket is in progress it appends an `auto` note to the ticket chat ("P4 confirmed still valid"), which the report brief includes.
6. The spec links the impact list to "the trace view", which does not exist (the Trace tab is a placeholder). Affected IDs open the Requirements or Diagrams tab, files open the Code or Tests tab via the existing `showFile`.
7. The MCP drift path reuses the Code tab: an MCP write is followed by Check again, and the same "Open drift ticket" button appears when the stored P4 checks are current and show drift. MCP runs get no `ticketId`.
8. Entry phase per kind (validated by `write_ticket_plan`): `requirement` P1; `change` P1 or P2; `bug` P5; `drift` P2 with `direction: 'design'` or P4 with `direction: 'code'`. `direction` is allowed for drift only. `affectedIds` name existing IDs only; new requirements or elements are described in `steps`.
9. Creating a ticket needs P5 `approved` or `stale`, or an existing ticket (the same rule as the tab).

## Review Focus

1. A discard after triage, after the entry run, and after the report run puts the ticket back exactly (status, plan, report); a ticket created after the discarded run is untouched (Task 9).
2. `approvePlan` refuses while an earlier phase is not approved or stale and names that phase; a second ticket cannot go `in_progress` (Task 9).
3. Close is refused while any walk phase is `stale`, `awaiting_approval` or `running`, naming the phase; a phase that is `not_started` is not in the walk (Tasks 7, 10).
4. `write_ticket_plan` and `write_ticket_report` are never offered over MCP and refuse in a run without `ticketId` (Task 3).
5. A P7 run never touches `state.phases`, never runs P4 or P5 checks, and its chat goes to `.aise/chat/TCK-xxx.jsonl` (Task 8).
6. Existing P1, P2, P4, P5 orchestrator tests stay green after Task 8 (run plumbing generalised, behaviour unchanged).

```ts
export const TicketKind = z.enum(['change', 'requirement', 'bug', 'drift']);

export const Direction = z.enum(['design', 'code']);

export const TicketPlan = z.object({
	entry: EntryPhase,
	affectedIds: z.array(z.string()),
	files: z.array(z.string()),
	steps: z.array(z.string().trim().min(1)).min(1),
	direction: Direction.optional()
});

export const ReportStep = z.object({
	runId: z.string(),
	phase: PhaseId,
	agent: z.string(),
	status: z.enum(['running', 'done', 'failed', 'discarded']),
	summary: z.string().optional(),
	files: z.array(z.string())
});

export const TicketReport = z.object({
	at: z.string(),
	text: z.string(),
	steps: z.array(ReportStep),
	changedIds: z.array(z.string()),
	files: z.array(z.object({ path: z.string(), diff: z.string() })),
	tests: z
		.object({ at: z.string(), passed: z.number(), failed: z.number(), outOfDate: z.boolean() })
		.nullable()
});

	id: TicketId,
	kind: TicketKind,
	title: z.string().trim().min(1).max(200),
	description: z.string().max(20000),
	status: TicketStatus,

});

export type TicketStatus = z.infer<typeof TicketStatus>;
```

```ts
// core/tickets.ts
import { nextId } from './ids';
import { Ticket, TicketsDoc, type TicketKind } from './schemas/tickets';
import type { ProjectStore } from './store';

export const TICKETS_PATH = '.aise/tickets.json';

export async function readTickets(store: ProjectStore): Promise<Ticket[]> {
	return (await store.readJson(TICKETS_PATH, TicketsDoc))?.tickets ?? [];
}

/** Never backed up: discard restores tickets from RunMeta.prevTicket instead. */
export async function writeTickets(store: ProjectStore, tickets: Ticket[]): Promise<void> {
	await store.writeJson(TICKETS_PATH, TicketsDoc, { tickets });
}

export async function findTicket(store: ProjectStore, id: string): Promise<Ticket | null> {
	return (await readTickets(store)).find((t) => t.id === id) ?? null;
}

/** Replaces one ticket by ID; throws when it does not exist. */
export async function saveTicket(store: ProjectStore, t: Ticket): Promise<void> {
	const all = await readTickets(store);
	const i = all.findIndex((x) => x.id === t.id);
	if (i < 0) throw new Error(`Unknown ticket: ${t.id}`);
	all[i] = Ticket.parse(t);
	await writeTickets(store, all);
}

/** Appends an open ticket with the next free ID; tickets are never deleted, so IDs are never reused. */
export async function addTicket(
	store: ProjectStore,
	input: { kind: TicketKind; title: string; description: string }
): Promise<Ticket> {
	const all = await readTickets(store);
	const t = Ticket.parse({
		...input,
		id: nextId('TCK', all.map((x) => x.id)),
		status: 'open',
		createdAt: new Date().toISOString()
	});
	await writeTickets(store, [...all, t]);
	return t;
}

/** The ticket in progress, if any (at most one, spec rule 8). */
export const inProgress = (tickets: Ticket[]) =>
	tickets.find((t) => t.status === 'in_progress') ?? null;
```
