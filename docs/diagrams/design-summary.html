Design summary · Coding with AI · WS 2026

An AI-assisted software engineering environment

A local web workspace that takes a project from a vague idea to tested, deployed code, then keeps requirements, diagrams, code and tests aligned while it changes. The developer approves every phase; agents do the work.

01

Three ideas carry the design

Everything else follows from these. They target C2 (alignment under change) and C5 (requirement to diagram to code), the two criteria we want to be clearly best at.

One model, many diagrams

The design is one typed JSON file. Every UML diagram is rendered from it by plain code, so the LLM never writes Mermaid and the diagrams cannot contradict each other.

Shared IDs everywhere

REQ, UC, DSN and SEQ IDs appear in the requirements, the design, a @trace tag in the code and the test names. Any artefact leads to the others.

Drift is computed, not guessed

ts-morph extracts a class model from the code and compares it with the design. Each difference is a drift item; the developer picks the repair direction.

03

Architecture

One TypeScript package. The orchestrator is plain code; only the agents call LLMs. Agents never call each other: they hand off through files, so every step is inspectable.

06

Drift detection and repair

Runs after every code edit in the UI, when a project opens, and on demand. Deterministic and cheap: no LLM is needed to find drift, only to explain and repair it.

+
TaskService.archive() is in the code, missing in the design.
Update designUpdate code
~
Task.dueDate is Date in the design, string in the code.
Update designUpdate code
−
TagRepository (DSN-007) is in the design, missing in the code.
Update designUpdate code

Example drift items after a hand edit. The maintenance agent suggests a direction for each one; "Update design" may also suggest a new requirement. A basic sequence check (does the calling method call the target?) is second in the cut order; component level drift via dependency-cruiser comes after class drift works. Design types use TypeScript syntax, so loose types never show up as false drift.

Drift itemUpdate designUpdate code
missing in coderemove the element from the designimplement it
missing in designadd it to the design, link REQsdelete it from the code
changedtake the code's versionchange the code to match the design

Known limit: a class renamed in code without its @trace tag shows as one item missing and one added.

07

Change propagation in P7

The maintenance agent computes the impact from the trace links; the orchestrator re-runs the affected phases in order, in update mode (patch the affected IDs, never regenerate), each with its gate. The change report lists every artefact touched, with diffs.

Change kind (all four on the to-do app, three live)ReqDesignCodeTestsDeploy
Requirement change"Tasks get a due date"1234if
Design change"Split BookingService into two classes"check123if
Bug report"Done tasks reappear after a restart"linklink21if
Hand edit to codedeveloper adds a method in the editormaybe213if
where the change starts re-run in update mode, own gate only if the impact reaches it

A bug report starts with a failing test linked to the affected REQ and UC IDs, then the P5 fix loop runs. For a hand edit, drift detection finds the change first; choosing "update design" makes the design follow the code, and the agent may propose a new requirement. Stale phases show "Update" or "Still valid"; a later phase cannot be approved while an earlier one is stale.

08

Where everything lives

Files only, no database. JSON is validated with zod on every write; an invalid write fails the tool call and the agent gets the errors back.

A project folder

showcases/todo/ ├─ .aise/ │ ├─ state.json phase status, approval hashes │ ├─ requirements.json P1 source of truth │ ├─ design.json P2/P3 source of truth │ ├─ chat/<phase>.jsonl conversation per phase │ ├─ runs/<runId>/ events, cost, file backups │ └─ changes/CR-001.md change reports ├─ docs/ generated: requirements, │ design (Mermaid), trace ├─ src/app/ wiring, ignored by drift ├─ src/<component>/ one file per class ├─ public/ test/ └─ Dockerfile compose.yaml

Rules that keep it safe and simple

  • Generated code only runs in Docker. Tests, mutation runs and deploy checks never execute on the host.
  • Write scopes per agent. File tools reject paths outside the project and outside the agent's folders.
  • Discard any run. The write tool backs up a file before an agent first touches it; discarding restores the backups.
  • Readable on GitHub. docs/*.md are generated from the JSON, and GitHub renders their Mermaid diagrams.
  • Errors are explained. Tool and validation errors go back to the agent; API errors retry 3 times, then the UI offers Retry or Retry with Sonnet.
  • Secrets in .env. Gitignored, never committed.

13

Calls made, and what we cut first

Calls made in the design

  • Own agent loop over a framework: easier to explain, scope and log.
  • Mermaid over PlantUML: renders in the browser and on GitHub; use cases drawn as flowcharts.
  • No git inside projects: run backups give undo and diffs.
  • Routes are controller classes; wiring in src/app/ is outside drift.
  • Non functional requirements link to components or nodes, or are "verified manually".
  • Update mode patches, never regenerates; hand edits survive.
  • Multi service auction is one codebase with several entry points.
  • Docs: README, ARCHITECTURE (living), CHANGELOG, decisions.md. No PRODUCT.md or PRD.md.

Cut order if we fall behind

  1. P3 self review
  2. Sequence drift
  3. Activity diagrams
  4. Trace view as a plain list
  5. Smaller auction showcase

Expected limits: the auction showcase will stress real time tests, sequence diagrams for concurrent bidding, and the external API (Frankfurter exchange rates, mocked in tests). Renames without @trace tags show as remove plus add. We document what breaks.
