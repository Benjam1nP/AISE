# Changelog

## Unreleased

- Architecture diagram: ARCHITECTURE.md has an agents and artefact flow section with a Mermaid diagram (every agent with its model, the tool registry, MCP, Docker, the artefact files and the P5 fix loop handoff) and a table of each agent's responsibility and why it runs on its model. An overview for slides and the report is in `docs/diagrams/agent-architecture.html` with SVG and PNG exports; the README shows the PNG.
- Hand in layout: `showcases/` holds only the three showcases (index in `showcases/README.md`), the P2 fixture moved to `test/fixtures/projects/todo/`, and the new `evidence/` folder maps each grading criterion to its evidence; the scaling notes moved to `evidence/scaling-comparison.md`. Course slide PDFs and the third party skills in `.claude/skills/` are no longer tracked.
- P3 design review in the UI. P3 is a station of the phase rail once the design has started. Its panel has Review design and shows the review agent's proposals (0 to 5: missing class or method, unclear responsibility, uncovered acceptance criterion, sequence mismatch) as cards with their kind, change and linked element and requirement IDs. Accept makes the design agent apply it (every diagram changes together), Reject needs no run, Discuss opens the design chat with the proposal in the composer. Resolved proposals are collapsed, and P3 shows stale when the design changed since the review. A review also runs by itself after every design run that changed the design (not after one that applied a proposal), so a design change now costs one more agent run. P3 does not gate code generation.
- Fix loop: the test agent and the code agent work together on failing tests. A Fix automatically button in the Tests tab (shown when the results are current and a finding is open or a failure has no explanation; Explain failures becomes the secondary button then) starts one run that alternates triage, a code fix and the checks for up to 3 rounds, with a $3 cost guard and 2 attempts per test. The code agent answers each finding with the new `report_fix_result` tool (fixed, needs a design change, test looks wrong); a disputed test goes back to the test agent, and a test the triage changes twice stops the loop. The loop also starts by itself when test generation leaves an open code bug, so approving P4 can now spend up to $2 for the tests plus $3 for the loop without another click. Every handoff shows in the chat and the live run as a message from one agent to the other ("Test agent to Code agent") and is logged as an `agent_message` event. Discard last run undoes the whole loop. `scripts/smoke-p5.ts --fix-loop` runs it live.
- Code workers treat state changes as binding: the sequence calls in the brief are the minimum, and before a call that saves an entity the worker sets every attribute the acceptance criteria change. Auction showcase: `Item.recordBid` is in the design and in SEQ-003 before `saveItem`, so `placeBid` updates the highest bid; REQ-008 trims display names; REQ-003 refreshes the item on a bid event, reloads the open list on a close event (closed watched items stay visible with their winner) and retries a failed live config fetch; `ItemStore` stores dates as ISO 8601 TEXT; `AuctionCloser` rejects an `intervalMs` that is not a positive integer. P4 and P5 regenerated from scratch; a P4 chat run then repaired what the regeneration dropped (converted highest bid, "You won!", socket error handling in the live server) and a P5 chat run added tests for the closer guard and the date columns (gates 5/5 and 4/4, 45 tests pass). Showcase `data/` folders are gitignored.
- Auction showcase: `EventFeed` holds the sockets of the connected live servers (`clients: Set<WebSocket>`) and the API entry adds each socket on upgrade, so `main.ts` no longer casts to the feed's private ws server. P4 regenerated; P5 caught the missing highest bid update again, which the P5 fix flow repaired.
- P6 deployment: approving P5 over a passing gate starts the deploy agent (Sonnet, medium effort), and Generate deployment does it by hand after an override. It writes `Dockerfile`, `compose.yaml` and `RUN.md` from a plan derived from the design (one compose service per service node, its start script, port, peer URLs and a shared data volume, a literal placeholder for every other `process.env` variable the code reads, listed in "Change before real use" in `RUN.md`) and proves them with `deploy_check`; a run gets at most 3 checks and $1. The Deploy tab shows the three files read only and the last check per service (status, url, log tail) with Run deploy check, which needs no LLM and shows the Docker message when Docker is down. The P6 gate checks that the files exist, that `compose.yaml` matches the design and that the stored check passed on the current files (out of date after a hand edit; Approve with override as in P4 and P5). P6 has its own chat and Discard last run, goes stale when service nodes, links, start scripts or dependencies change (Update or Still valid), and the project `README.md` links to `RUN.md`. `deploy_check` takes several `urls` and stores its result in `.aise/checks/deploy.json`.
- `run_tests` skips test files under `.aise/`. A run backup of an older test file was collected as a test and failed to load, so the P5 gate failed after a P5 Update that changed a test file.
- P7 ticket based maintenance. Every change goes through a ticket (change, requirement, bug or drift) in the new Tickets tab, which opens once P5 is approved or stale (or once a ticket exists) and replaces the disabled Changes placeholder tab. The maintenance agent (Opus 5.5, medium effort, never writes a project file) triages it into a plan (entry phase, affected IDs, files, steps) or asks up to three questions in the ticket chat. Approve plan starts the entry phase; the walk then goes through the later phases with Update, Still valid and Approve, and Close needs every phase approved. Closing stores a change report: the runs, a diff per file, the changed IDs, the last test result and the agent's summary. Discard last run walks tickets back with the phases. A drift ticket opens from the Code tab when the checks show drift, repaired in the design or the code direction. P7 is a station of the phase rail with the ticket chat in the left pane. With P7 selected and the New ticket form open (or no ticket yet), a click on a diagram element adds its ID to the new ticket's description. An entry run that failed or was interrupted is started again from the ticket (Start the entry run again); Retry in the phase chat no longer resends only the plan line, and a failed close is started again with Close ticket. The design agent can now read the code (`code_model`). `scripts/smoke-p7.ts` runs one change ticket live (costs API credit, not in CI).
- Drift checks the browser page: when the design has client components, `public/index.html` must exist and its `@trace` comment must carry exactly their IDs and requirement IDs. A missing page, a missing comment, a missing or an extra ID is a drift item, so the P4 gate and the code agent's `detect_drift` catch a dropped or stale comment.
- Generated services check entity ids and state: a public method that takes an entity id rejects an empty one (400) and an unknown one (`<Entity> <id> not found`, 404) when it can reach the store, and a change to an entity with a status enum checks the status first. Stores of entities referred to by id get `findById`. Workers now see the calls their class makes in the design sequences. Auction regenerated (P4 and P5): a bid with an empty or unknown bidder, a listing by an unknown seller and a bid on a closed item are rejected; P5 caught a missing highest bid update, which the P5 fix flow repaired.
- Injection by role: a dependency on a collaborator (a class or interface with methods that no design class uses as a data type) is a constructor parameter even when it holds state, so a gateway with its sockets or a service with a cache is created once in the wiring and shared. Drift reports a dependant that uses such a class without taking it in its constructor. The design agent no longer strips attributes from classes others depend on, and gives a socket gateway its sockets as an attribute (`WebSocket` from `ws` is a known design type now); the wiring may not wrap or replace class methods. The auction showcase was regenerated: `LiveGateway` holds `sockets: Map<string, WebSocket>` and sends itself, the unread `outbox` and the `broadcast()` wrapper are gone, and `ItemController` takes the shared `ExchangeRateService`.
- The P4 gate has a fifth check, "App starts": after a passing typecheck every entry in `src/app/` starts in the runner container and must answer `GET /health` with 200 within 30 s. A failure names the entry and why (exit code, status, no answer), and the gate panel shows the end of its startup log. The code agent gets the same check as the `start_app` tool and runs it after wiring and updates. The booking and auction checks were rerun and pass.
- Designs with several service nodes: P4 writes one entry per node (`src/app/main.ts` for the node the browser reaches over http, `src/app/<node>.ts` with `npm run start:<node>` for each other one), each building only its own classes and listening on its own port variable. Nodes talk only over their links: a client class reads the peer URL from `<PEER>_URL` in its code, the receiver serves `/internal/` routes or a ws endpoint, and the browser gets the URLs of other nodes from `GET /api/config`. The start scripts in package.json follow the design after every P4 run, and Update asks to delete the entry of a removed node. `update_design` now refuses a dependency between classes on two nodes (it was a warning without a link; entities and enums excepted), a cycle of dependencies and a service node name that gives no usable entry name (`main`, `app`, a leading digit, or the same as another node; notes in parentheses do not count). The P4 gate checks every entry and names the missing ones; the generated README has a run line per node. The auction showcase was migrated (the `EventFeed` and `EventSubscriber` pair became `EventFeed` plus the client class `EventFeedClient`, the API node is now `API Server`) and regenerated: two live node instances both deliver a bid placed over HTTP.
- The browser is one component on the client node without classes: no TypeScript under `src/` for it, the page `public/index.html` carries `<!-- @trace DSN-xxx REQ-... -->` as its first line in `<head>`, and the trace of the component, its requirements and their use cases shows `public/index.html`. `update_design` refuses classes in a client component and names them. Changing a client component's requirements makes P4 stale, so Update brings the page comment along. The booking and auction showcases are migrated: their client classes and files are gone and P4 Update put the `@trace` line into their pages.
- Acceptance criteria coverage: after a clean save the design agent calls the new `report_coverage` tool and maps every acceptance criterion to the class method or sequence step that covers it (stored in `.aise/design-review.json`), tries once more for uncovered criteria and names what stays uncovered in its reply. The P2 gate shows "Acceptance criteria covered" as a warning, never a failure: it lists the uncovered criteria (`REQ-002 AC3`), or reads "not run yet" or "out of date" after a design change, and never blocks approval.
- Deployment links: the design has links between nodes (`from`, `to`, protocol http, https, ws or wss, optional label) and a `client` node kind for the browser. The deployment diagram draws its edges from these links, labelled with the protocol, instead of from class relations, and shows a client with components as a dashed subgraph; `docs/design.md` lists the links under the nodes. A link to a database uses protocol `sql`. `update_design` requires `links`, refuses a link to an unknown node or to itself, a duplicate link and an external node without a link, and warns about a component on a database or external node and a dependency between two nodes that no link connects. A link change makes P4 stale for both nodes. A storing class on a client node gets no database. The booking and auction designs are migrated (auction drops its `FrankfurterApi` class); their code shows as stale until it is regenerated.
- Workspace tweaks: the code tab has Copy file and Full screen buttons; the chat stays in view while the right side scrolls (from 960 px); Send and Approve have icons and the composer hint is gone; run costs moved from the footer into the phase rail, per phase under its status and the total at the end.
- The Code tab lists and opens the generated `README.md`; it stays out of the code hash and the agents' write scope.
- Drift checks relations: a dependency on a service, repository, controller or interface that the class no longer uses anywhere, and a constructor parameter of a design class type with no relation in the design (in either direction) and no attribute of that type, each with both repairs (change the code or the design).
- Design checks: `update_design` warns about a class or interface without attributes or methods and an enum without values (saved anyway; the design agent fixes or explains them), and every result, error or success, names the next free ACT, UC, SEQ and DSN ID, counting the saved design so a deleted ID is not reused.
- Code tab no longer moves the page: the file list, the code and the generation progress share one fixed height and scroll inside it, the shown file stays until the next one has loaded, and opening a file at a line scrolls the editor only. Check again and Discard last run are bordered buttons with an icon.
- Generated projects get a `README.md`, rendered from the design after every code run: how to run the project and which file holds which design class with its requirements. Generated classes get a one sentence summary and each public method a one line JSDoc comment.
- Animated icons: a check draws itself when a phase is approved, and gate checks, generated files and form fields draw their check or alert when they change. They play only on a change seen on screen, never on page load or a tab switch, and not under reduced motion. The Aria Icons MCP server is configured in `.mcp.json` for finding icons.
- P4 code generation keeps data across restarts: every Repository, Store or Dao class outside an external node gets the SQLite database, with or without a database node in the design, and `src/app/main.ts` opens `DB_PATH`, default `./data/<project>.db` (`:memory:` allowed for tests). Ids are `randomUUID` strings created by the class that creates the entity, and storing never replaces another row. Each worker's brief lists the values of every enum the classes it uses name, and a first attempt gets no `read_file`, so it works from the brief instead of files other workers have not written yet.
- Generated projects get `package-lock.json` (the runner's lock, renamed) next to the scaffolded `package.json`, so a Dockerfile can install with `npm ci`; plain `npm install` crashes on this dependency set.
- P5 testing: approving P4 with a passing gate (or Generate tests) plans one test file per use case and writes it with Haiku workers in parallel rounds (retry only for a tsc error, a file that does not load or a criterion without a test, third attempt on Sonnet; a run stops above $2). Every acceptance criterion becomes a test named `REQ-001 AC2: ...` (`it.todo` with `manual:` for criteria that cannot be automated), so criteria trace to tests and results. Tests are written from requirements, design and `code_model` (now also listing HTTP routes), never from `src/` bodies. A Sonnet test agent triages failures: it fixes a test that contradicts the requirements or API and records the reason, or reports a code bug with an explanation and proposed fix; a test it changed without a report is recorded automatically. Apply fix lets the code agent patch `src/` from a finding (Discard restores it); Run tests re-runs the suite without an LLM. The P5 gate (tests exist, every must criterion has a test, typecheck, all pass) reads stored checks and shows "out of date" after a hand edit (coverage included, and Apply fix waits for a new Run tests); P5 has its own chat, turns stale when a requirement or use case changes (Update or Still valid), and the Tests tab shows results by use case, findings, corrected tests and the files read only.
- Explain failures: after a hand edit and Run tests, the Tests tab offers Explain failures for failing tests without a finding; the test agent triages only those, and its findings get Apply fix. A finding resolves once its test passes or is renamed or removed (a test file that fails to load leaves it open); resolved findings stay listed (the 50 most recent) and never reopen. P5 actions now also need P1 approved and P2 approved and not stale, and say which phase to fix first. Discarding a P5 run that changed no file keeps the current test results. The Apply fix brief names the test file correctly and forbids changes to `tsconfig.json` and `package.json`.
- Tests: a Docker test runs the real P5 checks on a fixture project (`test/fixtures/p5/`, green and with one broken method), and `scripts/smoke-p5.ts` runs code and test generation live (costs API credit, not in CI).
- Showcases: `showcases/booking/` and `showcases/auction/` taken through P1 to P4 with all artefacts, chat and run logs; scaling findings in `docs/reflection/showcase-scaling.md`.
- `trace` tool for the code and maintenance agents: from a requirement, use case, sequence, design element or actor ID to the linked requirements, design elements, code files and lines, and tests with their last result; without an ID, one row per requirement flagged when it has no design element or no test.
- P4 code generation: approving P2 (or Generate code) plans one file per design class, writes them with Haiku workers in parallel rounds (retry with the errors, third attempt on Sonnet), then a code agent writes the Express wiring in `src/app/` and a page in `public/`. Typecheck and drift decide when a file is done; a run stops above $3. The P4 gate shows typecheck and drift from stored checks and reads "out of date" after a hand edit or a design change. P4 has its own chat, turns stale when the design changes (Update or Still valid), and the Code tab shows the files read only with per file progress.
- `detect_drift` compares the code with the design (missing, extra and changed classes, members, REQ IDs, enum values, inheritance; a public member that implements or overrides a member of a design base is not extra); `delete_file` lets the code agent remove files, backed up per run.
- Tests: a Docker test runs the real checks on a hand written fixture project (`test/fixtures/p4/`), and `scripts/smoke-p4.ts` runs the whole pipeline live (costs API credit, not in CI).
- New look: graphite palette, Archivo display type, a drafting dot grid and a phase rail that shows all seven phases on one track with their status. Sticky header, home page with an introduction to the phases and project rows, lighter requirements table, chat bubbles, quieter cost footer. Awaiting approval is now orange everywhere.
- Run costs: the system prompt and tools stay cached for 1 hour across review gates (1 hour writes priced at 2x input), Sonnet 5.5 cache reads priced at 0.10/MTok, and Opus 5.5 runs only at medium effort (other efforts are refused before any API call).
- MCP server (`npm run mcp`): the project's tools over stdio for Claude Code or MCP Inspector, limited per agent with `--agent`. Writes made over MCP are recorded as a P7 run with backups; Discard for these runs is not in the UI yet (P7 work). MCP writes skip the phase gates: P1 does not reopen and P2 is not marked stale.
- File tools for agents (`list_files`, `read_file`, `write_file`, `delete_file`) with per agent path scopes; `package.json` may only use the fixed stack.
- `code_model`: exported classes, interfaces, functions, types, enums and consts with signatures and `@trace` tags, no bodies.
- `typecheck` and `run_tests` run generated code in a locked down Docker container and return errors and test results as data; `deploy_check` starts the project with Docker Compose, checks the health URL (default `http://localhost:8080/health`, at most 180 s) and always tears it down. Compose's own reading of compose.yaml must pass a short allowlist (ports on `127.0.0.1` only, no `image`, no `$`) and is exactly what runs, and Docker never sees host secrets such as the API key. The health probe only reaches ports compose.yaml publishes and does not follow redirects.
- The code agent may write `tsconfig.json`, and `typecheck` suggests one when it is missing. Path deny rules ignore case. A timed out runner container is removed even when the timeout hit before it started. The tools load when the server is started outside the repo folder. Docker works on WSL without Docker Desktop's WSL integration.
- Approving a design that was made before the latest requirement changes marks it stale at once and names the changed IDs.
- Discard last run refuses when the files changed after the run (an edit or an approval), instead of silently undoing them, and offers the earlier run once the latest is discarded.
- A run that ends over an unreadable artefact no longer leaves its phase stuck in running.
- CI also runs a secret scan (gitleaks) and `npm audit --audit-level=high`.
- Diagram playground: zoom with the wheel, buttons or plus and minus, drag or arrow keys to move, fit to view and full screen. Clicking an element still adds its ID to the chat.
- Removed hint texts under the diagrams, the chat composer and the tabs; an empty message is not sent and focus returns to the message box.
- Cheaper runs: the design agent uses Sonnet 5.5 at medium effort, and the write tools take the document directly, so the first write no longer fails. Measured: a requirements round $0.018 (was about $0.05), a design run $0.11 (was $0.40).
- Design system foundations: tokens, light and dark theme, self hosted fonts, guardrail tests (`docs/design-system.md`).
- Design system components in `src/lib/ui/` (atoms, composites, layout patterns) and the `/dev/ui` showcase with variants, states, props, code and token foundations (dev builds only).
- Interaction patterns in the design system: field error, success, loading and disabled states, validation timing helper, delayed Spinner and Skeleton, and the `ThinkingOrb` agent activity indicator.
- Workspace shell: project list and create form, project page with phase bar, chat (streamed agent text, collapsed tool calls, thinking orb, retry and discard of a failed run) and cost footer, live updates over server sent events with a reconnect banner.
- Requirements panel (table, editing, add and remove, open questions, assumptions, out of scope), diagrams panel (use case, class, sequence, deployment drawn in the browser, click an element to add its ID to the chat), approval panel with gate checks, run summary and discard, and a banner for requirements that changed after the design was approved.
- Requirements agent (P1) and design agent (P2) with validated tools; requirements and design are written as JSON and rendered to Markdown and Mermaid.
- Orchestrator: one run per project, approval gates with Approve anyway (P1) and override (P2), staleness of an approved design when requirements change (Update or Still valid), Discard last run that restores files and the earlier phase state.
- A run that leaves an approved artefact unchanged (for example a question) keeps the approval.
- Chat messages of a discarded run stay visible, marked as discarded, and are no longer sent to the agent.
- Removing a requirement asks for confirmation and unlinks it from open questions.
- Diagrams stay valid with quotes, semicolons and `#` in names; member names and enum values must be code identifiers, and every class must belong to a component.
- `.env.example` binds the server to `127.0.0.1`; Node 22.9 or newer is required.
