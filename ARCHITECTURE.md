# Architecture

Status: week 2: P1 (requirements), P2 (design), P4 (code generation), P5 (testing), P6 (deployment) and P7 (ticket based maintenance) built end to end in the workspace UI; the MCP server is built. The frozen design record is `docs/superpowers/specs/2026-11-04-ai-se-environment-design.md`. This file is the living architecture.

## Overview

```
Browser (SvelteKit UI) <-- SSE events / HTTP actions --> SvelteKit server
                                                          ├─ Orchestrator (plain code: phases, gates, staleness)
                                                          ├─ Agents (LLM loop: prompt + model + tool subset)
                                                          ├─ core (schemas, validation, render, tools, runs)
                                                          └─ core tools ──> Docker runner (typecheck, tests) and compose (deploy check)

MCP client (Claude Code, Inspector) ──stdio──> MCP server (`npm run mcp`) ──> the same core tools
```

One tool registry, two transports: our agents call `executeTool` in process; `src/lib/server/mcp/` serves the same `TOOLS` over stdio for any MCP client. Every call is validated by the same zod schema and limited by the same agent scope either way.

## Modules (as built)

- `src/lib/server/agents/`: our own agent loop (`loop.ts`, turn limit 30, SDK retries), agent definitions, cost accounting and the gate summary.
- `src/lib/server/orchestrator/`: `Orchestrator` (plain code: one action or run per project, phase state, gates, staleness, discard), gate checks, requirement hashes for staleness, the P4 rules (`p4.ts`), the P5 rules (`p5.ts`), the ticket walk rules (`tickets.ts`, pure functions that take the phase order as a parameter) and the event bus.
- Tickets: `core/schemas/tickets.ts` (zod), `core/tickets.ts` (store for `.aise/tickets.json`, ticket chat files), `core/ticket-report.ts` (report data), `core/tools/tickets.ts` (the three ticket tools) and `agents/maintenance.ts` (the agent and its briefs).
- `src/lib/server/codegen/`: the P4 pipeline: `plan.ts` (one file per class), `scaffold.ts` (`package.json`, `tsconfig.json`), `generate.ts` (rounds, escalation, wiring, final checks).
- `src/lib/server/testgen/`: the P5 pipeline: `plan.ts` (one test file per use case), `generate.ts` (rounds, escalation, triage, final checks). The agent definitions are `agents/test-worker.ts` and `agents/test.ts`; the P5 rules (`p5.ts`, `testGate`) live in the orchestrator folder.
- The P6 pieces are `core/deploy-plan.ts` (pure plan, compose check, staleness hashes), `core/deploy-env.ts` (extra env variables), `core/deploy-state.ts` (stored check and its files hash), `agents/deploy.ts` and `orchestrator/p6.ts` (readiness, `deployGate` inputs, `generateDeployment`, `checkDeploy`).
- `src/routes/`: project list, workspace page with form actions, and the SSE endpoint.
- `src/lib/ui/`: the design system (tokens and components); `src/lib/components/` holds the workspace panels built from it.

- `src/lib/server/core/tools/`: the registry (`TOOLS`, `executeTool`), per agent tool lists and path scopes (`scope.ts`, shared by agents and MCP), file tools, `code_model` (ts-morph, signatures only), `detect_drift` (`drift.ts`, comparison in `core/drift.ts`; `injectable` decides which dependencies are constructor parameters, shared with the worker shapes; `pageDrift` compares the `@trace` comment of `public/index.html` with the client components), `typecheck` and `run_tests` (`check.ts`), `start_app` (`start.ts`), `deploy_check` (`deploy.ts`: several urls, result stored by `core/deploy-state.ts` in `.aise/checks/deploy.json`, 3 checks per agent run through `ToolContext.deployChecks`). `core/code-state.ts` holds the code hash, the design hashes, the design hash of the stored checks and the stored P4 checks; `core/test-state.ts` the test hash, the test name contract (`parseTestName`), `coverage`, the report tools' storage and the stored P5 checks. `report_coverage` (`coverage.ts`, design agent only): after a clean save the design agent maps every acceptance criterion to the `{ classId, method }` or `{ sequenceId, step }` that covers it, all rows checked against the saved design and the requirements, stored as `.aise/design-review.json` with the design hash; the P2 gate reads it as the advisory check `Acceptance criteria covered` (`GateCheck.advisory`: shown as a warning, never counted in `passed`, in the approval conflict or in an override; detail is the uncovered list, `not run yet` or `out of date` when the design hash differs). `trace` (`trace.ts`, rules in the pure `core/trace.ts`): from a REQ, UC, SEQ, DSN or ACT ID to the linked requirements, design elements, `@trace` code locations and P5 tests with their last status, or without an ID the per requirement matrix with `noDesign` and `noTest` flags; `writeTraceDoc` renders the matrix as `docs/trace.md`. After every run that may change `src/`, the orchestrator renders the project `README.md` from the design (`writeReadme` in `orchestrator/p4.ts`, `readmeMarkdown` in `core/render/markdown.ts`).
- `src/lib/server/core/docker/`: the only place that calls the Docker CLI, always with a minimal environment (no host secrets). Generated code runs in the runner image (`runner/`): no network, project mounted read only, 1 CPU, 1 GB, 256 processes, read only root, all capabilities dropped, non root user, killed at the timeout inside and outside the container.
- Exception, known limit: `deploy_check` builds the deploy agent's Dockerfile with network on the host's Docker daemon, and the app can reach `host.docker.internal`. compose.yaml is checked as text (plain ASCII, no `$`, no `env_file`/`include`/`extends`), then Compose's own `config --format json` output must pass an allowlist (`tools/compose-check.ts`), and that JSON, written outside the project, is what `up`, `logs` and `down` run. The Dockerfile is not checked.
- Known limit: `test/docker/check.test.ts` compares the global list of runner containers before and after a test. `npm run test:docker` therefore runs its files one at a time (`--no-file-parallelism`); two test runs at once on one Docker daemon can still make it fail.
- `src/lib/server/mcp/`: stdio MCP server, one project per process, tools filtered by `--agent`. Writes are recorded as P7 runs with backups; they skip the phase gates, and Discard for them is not in the UI yet. They do not refresh the project `README.md`; the next code run does.

Server code uses relative imports and `process.env` only, so tsx scripts and the MCP entry can import it.

## Design model

`.aise/design.json` (`core/schemas/design.ts`) holds actors, use cases, classes, components, deployment nodes, links and sequences; every diagram is rendered from it. A node is a `service` (runs our code), `client` (the browser), `external` (a system we call and do not build) or `database`; only service and client nodes hold components. A component on a client node is the browser page `public/index.html` and holds no classes (a validation issue): `planCode` gives no file to a class on a client node (a design saved before that rule), the wiring and update briefs name the client components and the `<!-- @trace DSN-xxx REQ-... -->` comment that is the first line in `<head>`, a client component's P4 hash covers its reqIds (service components hash as before), the shared helper is `clientComponents` in `core/client.ts`, and `core/trace.ts` gives the component the code location `public/index.html` (comment line, else 1) when the file exists, reached from its node, its requirements and the use cases of those requirements. A link (`from`, `to`, `protocol` http, https, ws, wss or sql for a database, optional label) runs from the node that opens the connection; links have no ID and are not traced, but a node's P4 hash covers its links. `update_design` requires `links`; a stored design without them reads as `[]`. Validation blocks unknown or equal link ends, duplicate links (same ends and protocol), an external node without a link, a `dependency` between classes on two different nodes when the target has methods (a call to another node is a client class on the calling node plus a link) and a cycle of `dependency` relations (it names the cycle), and warns about a component on a database or external node. Associations and inheritance across nodes stay allowed. The deployment diagram draws edges from links only, a client node with components as a dashed subgraph.

## Tool scopes

| Agent       | Writes                                                                          | Reads                                                   |
| ----------- | ------------------------------------------------------------------------------- | ------------------------------------------------------- |
| code        | `src/`, `public/`, `package.json` (fixed stack only), `tsconfig.json`           | whole project                                           |
| test        | `test/`                                                                         | whole project except `src/` (uses `code_model` instead) |
| deploy      | `Dockerfile`, `compose.yaml`, `RUN.md`                                          | whole project                                           |
| maintenance | `.aise/tickets.json` through `write_ticket_plan` and `write_ticket_report` only | whole project, tickets and `trace`                      |
| others      | none                                                                            | whole project                                           |

Always refused: absolute paths, `..`, links leaving the project or its scope, `.aise/`, `.env*`, `.git/`, `node_modules/`, files over 200 KB.

The code agent writes the wiring after generation, answers P4 chat requests, patches the code in an Update run and in an Apply fix run (40 turns per run, a worker gets 6). The test agent triages failing tests, answers P5 chat requests and patches tests in an Update run (30 turns; a test worker gets 8). Prompts for both share the stack rules in `agents/stack-rules.ts`. The deploy agent writes the deploy files in a generate run, patches them in an Update run and answers P6 chat requests (`agents/deploy.ts`: the prompt lists the compose keys the checker allows, generated from `compose-check.ts`).

The maintenance agent triages a ticket into a plan and writes the prose of the change report (20 turns per run). It runs on Opus because it reasons over every artefact at once: which requirement, use case, class and test a change touches, and in which phase the change must start. Its only writes are the two ticket tools, which run bound to a ticket (see below).

Opus 5.5 runs at medium effort only (`callModel` refuses other values). Caching: a 1 hour breakpoint on the system prompt (tools and system are shared by every run of an agent, across review gates) plus the automatic 5 minute breakpoint on the conversation tail; the gate summary skips the tail breakpoint.

## Code generation (P4)

Starts when P2 is approved (and the design passes `validateDesign`) or from the Generate code button; it needs no code under `src/` yet. Afterwards the code changes through the P4 chat or Update.

1. **Plan** (`plan.ts`, plain code): one file per design class at `src/<component in kebab case>/<ClassName>.ts`, plus the class IDs each class uses. Workers get design signatures, not files, so a cycle of relations cannot deadlock.
2. **Scaffold** (`scaffold.ts`): `package.json` (dependencies of `runner/package.json`, `start` is `tsx src/app/main.ts`, plus `start:<node kebab>` per extra service node) and `tsconfig.json`, when missing.
3. **Workers**: up to 4 in parallel, one per file, with the class, the signatures of the classes it uses, its requirements and the declaration shape (`signatureOf`: the fixed constructor and the members it must implement from design interfaces). Dependency targets that are collaborators (a class or interface with a method that no design class uses as a type of an attribute, a parameter or a return type, whether or not it holds state) are constructor parameters; `update_design` warns when a dependency target is used as a type, because the dependant would build its own copy. A worker can write only its own path (`ToolContext.writeOnly`); its tool calls go to the run's `events.jsonl` as `worker` entries and are not streamed.
4. **Rounds**: after each round one `typecheck` and one drift check decide which files are ok. A failing file retries with its own tsc errors and drift items. Attempts 1 and 2 are Haiku, attempt 3 Sonnet. A worker that did not write its file fails the attempt.
5. **Wiring**: the code agent writes `src/app/` (Express routes, `createApp`, `main.ts`) and `public/index.html`, then runs `typecheck` and `detect_drift` until both are clean, then `start_app` until every entry answers `GET /health`. Drift ignores `src/app/`; tsc does not.
   **Several service nodes** (`core/nodes.ts`, `serviceNodes`): the primary node is the target of the first link from a client node to a service node over http or https, else the first service node; a service node's entry name (`nodeKebab`, notes in parentheses dropped) must start with a letter, not be `main` or `app` and be unique (validation); it keeps `src/app/app.ts` (`createApp`) and `src/app/main.ts` on `PORT` (8080) with only its classes. Every other service node gets `src/app/<node kebab>.ts` on `<NODE>_PORT` (8081, 8082, ... in design order), with its own classes, `GET /health`, its routes and the endpoints of its incoming links. A client class has no URL attribute and reads the peer URL from `<PEER>_URL` (default `http://` or `ws://localhost:<peer port>`) in its own code; the receiver serves an http link as routes under `/internal/` and a ws link at `/internal/<caller kebab>`, where a feed sends to every connected socket. `createApp` takes db only when a class on the primary node stores data. After every P4 run the orchestrator sets the `start` and `start:<node>` scripts of package.json from the service nodes and rechecks when it changed them; the Update brief lists entries of removed nodes for deletion. For a browser link to another node the primary serves `GET /api/config` with `{ "<node kebab>": <NODE>_PUBLIC_URL }`. The wiring and update briefs list this per node; with one service node they are unchanged. The README gets one run line per node.
6. **Checks**: the run ends with `runCodeChecks` (typecheck in the runner image plus drift), stored in `.aise/checks/P4.json` with the code hash and the design hash.

Cost guard: when a round ends above $3 no more workers start, the wiring is skipped and the run is `failed`. The run is also `failed` for an API error or a typecheck timeout or error; files that fail after three attempts leave the run `done`, and the gate shows them.

**P4 state.** The code hash covers `src/`, `public/`, `package.json` and `tsconfig.json`. The gate (`Code exists`, `App entry exists`, `Typecheck passes`, `Code matches the design`, `App starts`) reads the stored checks (and the file list for the entries: `src/app/main.ts` and each extra node's, the detail names the missing ones) and shows "out of date" when their code hash or design hash differs from the current ones, so neither a hand edit nor a design change (Still valid) shows an old green result. `App starts` (`start_app`, `core/tools/start.ts`) runs only after a passing typecheck: every existing entry starts at once with tsx in one runner container (no network but loopback, project read only, `DB_PATH` in `/tmp`), and each must answer `GET /health` with 200 within 30 s; a failure names the entry and its reason and the gate panel shows the end of its log; the Code tab then runs the checks on open. P4 keeps `designHashes` per class, component and node (only the fields code depends on); an approved P4 turns stale when the design on disk differs, and the developer chooses Update (the code agent patches the changed, added and removed IDs; its message carries the declaration shapes of the changed and added classes, and a done run adopts the new hashes even when it wrote nothing) or Still valid. P4 is a third chat phase, bound to the code agent. Its files are shown read only in the Code tab (`/p/<name>/file`), with per file progress from `codegen_file` events.

Tests: unit tests mock the agent loop and the checks; `test/docker/codegen.test.ts` runs the real checks on `test/fixtures/p4/` (a small hand written project: typecheck passes, no drift, and a changed method signature gives one `changed` item). `scripts/smoke-p4.ts` runs the whole pipeline live on the to do design; it costs API credit and is not in CI.

## Test generation (P5)

Starts when P4 is approved (and the project has a `package.json` and no file under `test/`) or from the Generate tests button; afterwards the tests change through the P5 chat or Update. The tests are derived from the requirements, the design and the code's API surface (`code_model`: declarations and HTTP routes), never from `src/` bodies: the test agent's scope refuses reads of `src/`.

1. **Plan** (`plan.ts`, plain code): one `test/<UC>.test.ts` per use case with the acceptance criteria of its requirements (numbered from 1 per requirement; a requirement linked to several use cases only in the lowest UC ID), its sequences and the classes it touches; requirements without a use case get `test/<REQ>.test.ts`. A use case without criteria and sequences gets no file.
2. **Naming contract**: `describe('UC-001 ...')`, `it('REQ-001 AC2: <criterion>')`, `it('SEQ-001 scenario: <name>')`, and `it.todo('REQ-007 AC1: manual: <reason>')` for a criterion that cannot be tested automatically. `parseTestName` reads the IDs back from Vitest results; `coverage` gives one row per acceptance criterion (passed, failed, manual or missing), which is what traces a requirement to a test and its last result.
3. **Workers**: up to 4 in parallel, one per file, each writing only its own path, with the plan entry, the requirement texts, the use case and sequences, the `code_model` declarations of its classes and the `createApp` signature with the routes (`code_model` is computed once per run).
4. **Rounds, structural retries**: after each round one `typecheck` and one `run_tests` decide which files are ok. A file retries only for a structural problem: a tsc error, a suite level failure (the file does not load) or a criterion without a test. A plain assertion failure never retries a file. Attempts 1 and 2 are Haiku, attempt 3 Sonnet; after that the file is failed.
5. **Triage**: when tests fail, the Sonnet test agent runs once with the failing tests, their messages and the log tail. A test that contradicts the requirements, design or API surface (wrong import, signature, route, setup) it rewrites and records with `report_test_fix`; a failure the code causes it records with `report_code_bug` (explanation and proposed fix) and leaves the test alone. Both tools append to `.aise/runs/<runId>/findings.json`. A test file the triage changed, added or deleted without a `report_test_fix` gets an automatic entry ("changed during triage without a report"), so no test changes silently.
6. **Checks**: the run ends with `runTestChecks` (typecheck, tests, findings merged: earlier findings stay while their test still fails, test fixes are kept as history), stored in `.aise/checks/P5.json` with the code hash and the test hash.

Cost guard: when a round ends above $2 no more workers start, the triage is skipped and the run is `failed`. The run is also `failed` for an API error, Docker down or a timeout; failing tests or files that fail after three attempts leave it `done`, and the gate shows them.

**Apply fix.** A finding shows its test, the explanation and the proposed fix with an Apply fix button. It starts a P5 run of the code agent with the finding, the test file and the failure; the agent patches `src/` (its scope forbids `test/`), and the run ends with the P4 checks and the P5 checks. Discard last run restores `src/` and the checks files. Apply fix needs current checks (Run tests first after a hand edit) and a finding whose test still fails. The fix brief carries the test file's path and its content, fenced apart from the failure output, and forbids changing `tsconfig.json` and `package.json`.

**Fix loop.** One P5 run (`RunMeta.fixLoop`, agent `test`) owns every round and alternates the two agents; plain code in `testgen/fix-loop.ts` runs the steps and switches `ToolContext.agent` per step, so each agent keeps its scope. A round has up to four steps: (1) triage by the test agent (30 turns), only when a failure has no open finding or the code agent disputed a test; (2) the handoff: open code bug findings whose test file exists, that the code agent has not declined and that have fewer than 2 attempts (counted per file and test name, since a new report gets a new finding ID) go to the code agent; (3) one code agent call (40 turns) with `fixLoopBrief`, which answers each finding with `report_fix_result` (`fixed`, `needs_design_change` or `test_looks_wrong`, stored in `findings.json` as `fixResults`; the tool exists for the code agent in fix loop runs only, a missing reply counts as fixed); (4) `runCodeChecks`, then `runTestChecks`, merged under the loop run ID. Problems the loop caused are those beyond a baseline taken at the start. The stored P4 and P5 checks are the baseline only when their hashes match the current files; otherwise the checks run once at the start, without an LLM, and a timeout there ends the loop `failed`. New typecheck errors outside `test/` and new drift items go to the code agent in the next round with the findings, and a loop that still shows them ends `failed`, never `done`. A test file that stops loading or gains typecheck errors under `test/` ends the loop at once, `failed`, with a checks to test message naming the files, since the code agent cannot change `test/`. Disputes: `needs_design_change` stays open for the developer and is not handed back; `test_looks_wrong` goes to the next triage with the code agent's reason, and when triage corrects the test the finding goes back to the code agent, while a repeated `report_code_bug` leaves it open for the developer. Stop rules: no test fails and no new problem (`done`); nothing left to do (`done`, failing tests stay for the developer); a round that changed no file under `src/` or `test/` (`done`, unless a dispute waits); round 3 finished (`done`); a triage step that changes a test file an earlier triage of this loop already changed, read from file snapshots (`done`, with a message that the test needs the developer); an agent error, a timed out check or Docker down (`failed`); cost above $3 (`failed`): each agent step gets what is left of the limit as its own hard guard, no step starts with less than $0.10 left, and the loop stops when a step hits its limit or the total reaches it. Triggers: the Fix automatically button in the Tests tab (`fixLoop`, needs P5 ready, current stored checks and an open finding or an unexplained failure, else a `ConflictError`), and a follow up hook in `execute`: when a generation run ends `done` with an open code bug finding, the loop starts on the same claim before it is released, so no other action can slip in and Discard undoes the fixes but keeps the tests. The loop leaves P4 approved and adopts no hashes, syncs the start scripts and renders the README like Apply fix, and Discard last run restores `src/`, `test/` and both checks files. Visibility: every handoff (test to code with the finding IDs and one line explanations, code to test with one line per reply, checks to test with the round result) is a bus event `agent_message { runId, from, to, text, findingIds }`, is written to `events.jsonl`, shows in the live run as a message between two agents and is appended to the P5 chat as an `auto` assistant entry with optional `from` and `to` (`test`, `code` or `checks`; old chat files still read). The test agent's history in later P5 chat runs keeps these lines. `scripts/smoke-p5.ts --fix-loop` runs the loop live after generation.

**Explain failures.** After a hand edit and Run tests, failing tests have no finding yet. When current results hold a failing test (not a file that did not load) without an open finding and no run is active, the Tests tab offers Explain failures (`triageTests`): a P5 run of the test agent whose only message is the triage brief with exactly those tests and the stored log tail. It ends with the P5 checks, which merge its findings and test fixes; a test file it changed without a report is recorded as in generation triage. This closes the demo path: hand edit, Run tests, Explain failures, Apply fix, green.

**Findings history.** A finding gets `resolvedAt` at the first check where its test passes, is todo or skipped, or is missing from a file that loaded or was removed (a suite failure of its file, a check without results or with a timed out run resolves nothing) and is kept as resolved; it never reopens, a new failure needs a new report. The checks keep the 50 most recently resolved ones.

**P5 readiness.** Chat, Generate tests, approve, Update, Still valid, Apply fix, Explain failures and Fix automatically need P1 approved and P2 and P4 approved and not stale; the refusal names the first upstream phase that is not ready. Run tests needs no approval. Discarding a P5 run puts back the checks saved at its start only when the run changed files; a run that changed none leaves the current checks.

**P5 state.** The test hash covers the files under `test/`; the P5 artefact hash covers code and tests, because Apply fix changes `src/`. The gate (`Tests exist`, `Every must criterion has a test`, `Tests type check`, `All tests pass`) reads the stored checks and shows "out of date" for the last two when the code hash or test hash differs, so a hand edit never shows an old green result; Run tests (`checkTests`, no LLM) refreshes them. A manual todo counts as covered, never as passed. P5 keeps `reqHashes` and `useCaseHashes` (name and requirement IDs of a use case; name, use case and messages of a sequence); an approved P5 turns stale when they change (a code change only makes the checks out of date), and the developer chooses Update (the test agent patches the test files of the changed IDs, writes files for new use cases and deletes those of removed ones) or Still valid. P5 is a fourth chat phase, bound to the test agent; the Tests tab shows results grouped by use case, findings, corrected tests, the gate and the test files read only.

Tests: unit tests mock the agent loop and the checks; `test/docker/testgen.test.ts` runs the real checks on `test/fixtures/p5/` (the P4 fixture code plus a hand written `test/UC-001.test.ts`: green with every must criterion covered, and a broken method gives exactly one failing test with its message). `scripts/smoke-p5.ts` generates the to do code and then its tests live; it costs API credit and is not in CI.

## Deployment (P6)

Starts when P5 is approved over a passing gate and the project has no deploy file yet (an override starts nothing paid) or from the Generate deployment button; afterwards the files change through the P6 chat or Update. P1, P2, P4 and P5 must be approved and not stale; the refusal names the first phase that is not ready.

1. **Plan** (`core/deploy-plan.ts`, plain code, no LLM): `deployPlan(design, packageJson)` gives one compose service per service node, named by `nodeKebab`, with an explicit `command` (`npm start` or `npm run start:<node>`), the port (8080 for the primary service, then 8081 and on; container and host port are equal) published on `127.0.0.1`, `<PEER>_URL` for each link using the peer's service name, and one shared named volume `data` at `/data` (`DB_PATH=/data/app.db`) for storing nodes. External and database nodes get no service. The agent's brief and the gate use the same plan.
2. **Extra variables** (`core/deploy-env.ts`): every `process.env.X` under `src/` that the plan sets on no service gets a literal placeholder of the type its name suggests (`3000` for `PORT`, `http://change-me.invalid` for `..._URL`, else `change-me-admin-password` style text) in every service and a "Change before real use" section in `RUN.md`.
3. **Agent**: Sonnet writes `Dockerfile`, `compose.yaml` and `RUN.md`, then calls `deploy_check` with every health url. A run gets 3 checks that reach `docker compose up` (a refusal or Docker down does not count) and a $1 cost guard; a cost limit is a failed run with its message. There is no second check after the run: the gate reads what `deploy_check` stored.
4. **Gate** (`checkDeployGate`): `Deployment files exist`, `Consistent with the design` (`composeProblems`: a service per service node and no extra, its command, every peer URL variable) and `Deploy check passed`. The stored check (`.aise/checks/deploy.json`, files hash of `Dockerfile`, `compose.yaml`, `package-lock.json` and the code, not `RUN.md`) reads "out of date" after a hand edit; a failed check names the service of each url without a 2xx answer, or shows the log line (Docker down, refused compose.yaml). Approve with override works as in P4 and P5.
5. **Check without an LLM**: Run deploy check (`checkDeploy`) calls the tool on the plan's urls. A refusal or Docker down is stored as a failed check; when the tool kept an earlier pass for the same files instead, the Docker message comes back as an error banner so the click is not silent.
6. **Staleness**: `PhaseState.deployHashes` cover per service node its name, planned environment, links and start script, plus the dependency lists. A change to any of them marks P6 stale (Update patches the files and lists added, removed and changed services; Still valid keeps them); a class edit does not. P6 is not judged while `package.json` is unreadable.
7. **UI**: the Deploy tab (`DeployPanel.svelte`) lists the three files read only, the last check as a table with one row per probed url (service name, status, url), the log tail and Run deploy check; `GenerateDeployment.svelte` starts a run when P5 was approved with an override. P6 has its own chat and Discard last run; every P6 run and discard renders the project `README.md` again, which links to `RUN.md` when it exists.

Tests: unit tests mock the agent loop and the tool; `test/docker/deploy.test.ts` runs `deploy_check` on a real two service fixture (`test/docker/fixtures/two-services/`). `scripts/smoke-p6.ts` generates the to do deployment live; it costs API credit and is not in CI.

## Tickets (P7)

Every maintenance change goes through a ticket of kind `change`, `requirement`, `bug` or `drift`. Tickets live in `.aise/tickets.json` (IDs `TCK-001` and up, never reused, never deleted); each ticket has a chat file `.aise/chat/TCK-xxx.jsonl`. Runs never back up `tickets.json`.

States: `open` (created, or the agent asked questions) -> `triaged` (a plan was written) -> `in_progress` (plan approved) -> `done` (change report written). `rejected` is possible from `open` and `triaged`. Only one ticket is `in_progress` per project, and one run per project stays the rule.

1. **Create.** Needs P5 approved or stale, or an existing ticket. Starts a P7 run of the maintenance agent in triage mode: it reads the artefacts, calls `trace` and `detect_drift`, then asks at most 3 questions or calls `write_ticket_plan` (entry phase, affected IDs, files, steps). The entry phase is fixed per kind in code: `requirement` P1, `change` P1 or P2, `bug` P5, `drift` P2 (`direction: 'design'`) or P4 (`direction: 'code'`).
2. **Approve plan.** The ticket goes `in_progress` and a normal chat run starts in the entry phase with the plan as its brief. Refused while an earlier phase is not approved, naming it. The orchestrator marks that run `RunMeta.entry: true`; only a done run so marked counts as the entry run (`entryRan`), so a Retry of the plain chat line does not. While a ticket is in progress and its entry run did not finish, Start the entry run again (`approvePlan` once more) sends the same brief. From here the existing staleness cascade does the propagation.
3. **The walk.** The walk is the chat phases (P1, P2, P4, P5, P6) from the entry phase on, read from state, minus phases that are `not_started`. The developer approves the entry phase, then uses Update or Still valid on each phase the cascade made stale (Check again before Still valid on P4), and approves it. Approving P5 in a walk on a project with no deploy file yet starts the first deployment, as outside a ticket; that P6 run belongs to the ticket in progress, so P6 joins the walk and must be approved before Close. Still valid starts no run, so while a ticket is in progress it appends an `auto` note to the ticket chat for the report.
4. **Close.** Allowed when every walk phase is `approved` and the entry run finished (`closeRefused`, one helper for the action and the view; Run tests first so the report reads current results). Close is a P7 run marked `RunMeta.report: true`, the only run that may call `write_ticket_report`. The orchestrator builds the report data in plain code (`ticket-report.ts`): the ticket's runs as steps, a net diff per file, changed requirement and design IDs, the last P5 result. The agent writes only the prose `text`, and the tool sets `done`.
5. **Rollback.** Every run started while a ticket is in progress records `ticketId` and `prevTicket` (status, plan, report before it). Discard last run restores them, so a discard after triage, after the entry run and after the report run puts the ticket back exactly, and a ticket created later is untouched. A close run that fails or is discarded puts the ticket back in progress.

The P7 rail status is derived in the snapshot, not stored: `running` while a ticket run is active, `awaiting_approval` while a ticket is `open`, `triaged` or `in_progress`, `approved` when all are `done` or `rejected`, `not_started` without tickets.

Drift tickets open from the Code tab ("Open drift ticket") when the stored P4 checks are current and show drift; no other drift ticket may be open, triaged or in progress. Writes made over MCP stay P7 runs without a ticket (no `ticketId`); after one, Check again shows the drift and the same button applies.

Tools: `read_tickets` (everywhere), `write_ticket_plan` and `write_ticket_report` (run bound: they find their ticket through the run's `ticketId`, refuse without one, are never offered over MCP, and the report needs the `report` flag). `trace` accepts a ticket ID and returns the ticket with its runs. Ticket titles, descriptions, diffs and notes reach the model fenced and are treated as data, never as instructions.

Known limits:

- Tickets open once P5 is approved or stale; they do not wait for P6.
- Affected IDs open the Requirements or Diagrams tab and files open the Code or Tests tab; the Trace tab is still a placeholder, so there is no graph view of a ticket.
- Report diffs are capped at 400 lines and 40000 characters per file, a file over 1 MB is not diffed, and only plain files at their own path are listed.
- A plan names existing IDs only; new requirements or design elements appear in its steps.
- Rejecting an `in_progress` ticket needs its runs discarded first.
- Discard last run of a P7 run (triage, a ticket chat answer, close, an MCP write) has no button yet: the gate offers Discard only for a run of its own phase and is hidden in P7, and while such a run is the latest kept run no gate offers Discard. The orchestrator's discard handles these runs (step 5).
- `scripts/smoke-p7.ts` is a live check, not in CI.

## Event flow

Form action -> `Orchestrator` (claims the project, records the user message and the phase state before the run in `RunMeta`) -> `runAgent` in the background -> tool calls (validated writes, files backed up per run) -> bus events (`run_started`, `agent_text`, `tool_call`, `agent_message`, `codegen_file`, `run_finished`, `changed`) -> SSE `/p/<name>/events` -> UI (`WorkspaceStream` folds the live run and reloads the snapshot on `changed`).

After a run, a phase that was approved (or stale) keeps that state when the run left its artefact unchanged; otherwise it reopens for approval. Discard last run restores the files and the phase state the run started from, then recomputes P2 staleness, and leaves the run's chat messages out of later agent history.

## Workspace UI (week 1)

- `/` lists projects and creates one (`create` action, validated with `isValidProjectName` on the server). `/p/<name>` is the workspace: phase rail (`PhaseBar.svelte`, all seven phases with their status and cost), chat bound to P1, P2, P4, P5 or P6 (or to a ticket, see below), artefact tabs (Requirements, Diagrams, Code, Tests, Deploy, Tickets, Trace); run costs show in the phase rail.
- Form actions on `/p/<name>` (`send`, `approve`, `stillValid`, `update`, `generate`, `checkCode`, `generateTests`, `checkTests`, `triageTests`, `fixLoop`, `generateDeployment`, `checkDeploy`, `applyFix`, `discard`, `editRequirements`, and the ticket actions `createTicket`, `ticketSend`, `approvePlan`, `rejectTicket`, `closeTicket`, `openDriftTicket`) call the orchestrator; `src/lib/action-errors.server.ts` maps `ConflictError` to 409, `PathError` and zod errors to 400 and `NotFoundError` to 404, always with a plain `message`.
- `/p/<name>/events` streams the project's bus events as server sent events (`data: <json>`, a `: ping` every 15 s). `WorkspaceStream` (`src/lib/workspace-stream.svelte.ts`) folds them into a live run (`src/lib/live-run.ts`) and calls `invalidateAll()` on `changed` and `run_finished`. After a reload the live part starts from the current event on; earlier streamed text is not replayed.
- The right column of the workspace shows, top to bottom: `StaleBanner` (only when `staleReqIds` is not empty), `GatePanel` (gate checks of the selected phase, Approve, Approve anyway for P1 open questions, Approve with override for P2, and the only Discard last run entry), and the artefact tabs. `RequirementsPanel` edits post the whole document to `editRequirements`. `DiagramsPanel` draws the Mermaid sources of the snapshot with `Mermaid.svelte`, which imports `mermaid` in the browser and registers `window.aiseSelect` so a click on an element calls `Chat.insert`; with P7 selected and the New ticket form open (or no ticket yet) the page appends the ID to the new ticket's description instead, which it keeps so it survives the tab switch.
- **P7 station.** P7 is a station of the phase rail, shown once the Tickets tab is open (P5 approved or stale, or a ticket exists). Picking it opens the Tickets tab, swaps the left pane for the chat of the selected ticket (the ticket in progress, else the newest; a new ticket is selected at once) and hides the phase gate and the stale banner, since a ticket step carries its own Update, Still valid and Approve. Typed text stays with its ticket. Below `md` the chat keeps the pane until a plan ID or file or an Open phase button is used, which switches to the Artefacts pane. The Tickets tab lists tickets with a create form (kind, title, description), the plan with Approve plan and Reject (a drift ticket also picks the direction), the walk steps with the phase actions, Check tests and Close, and the change report with its diffs. Ticket errors name the field.
